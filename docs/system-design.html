Civitone System Design

A district audio system for a downtown. Six speaker nodes on poles, one controller, one web console. Nodes are adopted once and then work from any network, and a live announcement reaches every zone within a quarter second.

A node holds two outbound connections to the controller: a control channel (WebSocket, TLS, authenticated by device token) for status and commands, and an audio channel (Snapcast client protocol, TCP) for the stream. Both reconnect on their own. That is the whole protocol surface of a node.

02

Inside a node

Firmware is a fork of the esparagus Snapcast client, so the audio path is already proven on this board. Civitone adds adoption, the control channel, and a persistent identity.

What lives in flash and survives reboots, power loss, and moving to a new network:

  • device_id: generated once at first boot, never changes. Shown on a label inside the enclosure.
  • device_token: issued by the controller at adoption. Authenticates the control channel.
  • controller_url: where to dial. Can be a hostname so the controller can move.
  • Up to four saved WiFi networks, tried in order.
  • Zone name, last known volume, last latency profile, so a node that reboots mid-event comes back the way it left.
Why
Volume is controlled at the DAC, not the amp. The amp pot is set once at install as a ceiling. This is the fix for the gain problem from the bench build: full-scale digital no longer slams the amp because the DAC never has to be at full scale.
03

Adoption

Modeled on how network gear is adopted by a controller. A node is a stranger until someone with console access claims it. After that it is trusted anywhere.

FACTORY
No WiFi, no identity. Broadcasts a setup network civitone-XXXX.
PROVISIONED
Has WiFi and the controller URL. Dials the controller with its claim code.
PENDING
Seen by the controller, listed in the console as "waiting for adoption". Can't play audio.
ADOPTED
Holds a device token. Named, assigned to a zone, fully controllable.
FORGOTTEN
Token revoked from the console. Node returns to Provisioned and must be re-adopted.

What the operator sees

A card appears at the top of the console: "Node 7F2A is waiting. Claim code 48-11-20." The claim code is printed on the node's label, so adopting the right one is a matter of reading the label and matching the code, then giving the node a name and a zone. The whole step takes about ten seconds and is the only time anyone has to think about a specific board.

Setup network details

  • The node brings up the setup network only when it has no saved WiFi, or when the button inside the enclosure is held for 5 s. Otherwise it never advertises anything.
  • The captive page accepts several WiFi networks at once, so a node can be given the shop network and the city network on the same bench visit.
  • Improv WiFi over serial is also accepted, so a batch of nodes can be provisioned from a laptop script without touching a phone.
04

Any network, even locked down

Requirement 3 is met by a rule, not a feature: a node never needs to be reached and never needs to see another node.

Locked-down WiFi usually means some mix of client isolation (devices can't see each other), no inbound connections, NAT, and a captive portal. The first three don't matter to Civitone because every connection is outbound from the node to the controller, on ports that any network already allows (443 for control, and the audio channel can share 443 or use its own port). Nodes on different networks, or on the same network with isolation turned on, behave identically.

Network conditionEffect on Civitone
Client isolation onNone. Nodes never talk to each other.fine
No inbound connections / NATNone. Controller never dials a node.fine
Only ports 80/443 allowedNone if the audio channel is served on 443 alongside control.fine
Captive portal (click to accept)Node can't click. City IT allowlists node MAC addresses, which the proposal already asks for.needs allowlist
Controller not on the same networkWorks if the controller is reachable by hostname. Adds latency equal to the path between networks.check latency
No WiFi at all at a poleNode stays offline and says so. Fallback is a travel router on the operator's cart.plan around it
Overlay
WireGuard is not needed for this. The control channel is TLS and the device token is the identity, so the overlay from the original plan goes away. If the city later insists on a VPN, the controller can sit behind one and nodes still only know a hostname.

Where the controller lives

At an event, the controller is on site: a Pi 4 in a case on the operator's table, with its own travel router. Nodes reach it either through the city WiFi (if it routes to the travel router's address) or by joining the travel router's network directly. Having the controller local is also what makes requirement 4 possible. Between events the controller can be off, or on a shelf at the shop so nodes can be tested remotely.

Every adopted node sends a heartbeat every 5 seconds. The controller marks a node degraded after 2 missed beats and offline after 6 (30 s).

Status is also pushed the other way. The console holds one WebSocket to the controller and gets every heartbeat as it arrives, so a node going quiet shows up within seconds without reloading the page.

Commands a node accepts

set_volume, mute, set_stream, set_profile, identify (plays a short tone so you know which pole you're looking at), reboot, update_firmware (over the air, from the controller), forget.

06

Latency

In a synced system, latency is the buffer. Nodes play audio exactly one buffer length after the controller received it. The buffer is what keeps six poles in step over imperfect WiFi, so the trade is between tightness and tolerance.

Parade 200 ms

Live announcer mic. Short enough that the voice on the speakers doesn't fight the voice in the air.

Music all day. Nobody can hear the delay, and the fat buffer rides out WiFi hiccups.

How 200 ms is reached

  • Controller on site. The mic plugs into the controller. No internet hop.
  • PCM, not a lossy codec. 48 kHz 16-bit stereo is about 1.5 Mbps per node, well inside what the city WiFi gave the Pi tests. No encoder delay.
  • Small chunks. 10 ms frames from the server instead of the default 20 ms.
  • Clean radio. The external antenna, and a travel router for parade day if the city network is busy.
  • PSRAM. The 8 MB on the Amped board holds the buffer comfortably at either profile.
Target
200 ms is the design target for the parade profile and 150 ms is the stretch. Below about 120 ms, ESP32 Snapcast clients start dropping on real WiFi. The first thing to measure on the bench is the lowest buffer two nodes can hold for ten minutes with zero dropouts; that number sets the parade profile.

Switching profiles is one button in the console. It is applied to every node at once, and the stream re-syncs in about a second.

07

Sources and routing

A source is anything the controller can turn into a stream. Routing is assigning zones to streams. Zones on the same stream are one synced group.

SourceHow it enters the controllerTypical use
Live micUSB audio interface, XLR inParade announcer, emergency message
MusicLine in from a laptop or phone; or a playlist on the controllerFestival background
AnnouncementsPre-recorded files, played from the console with one tap"Parade starts in 10 minutes", weather, lost child
Phone (Bluetooth)Controller pairs as a speakerQuick music from whoever is nearby
Network streamURLTown radio, remote feed

Routing in the console

  1. Tap one or more zone cards to select them.
  2. Tap a source. The selected zones switch to it together.
  3. Zones sharing a source show a Linked badge. They are sample-locked, not just "playing the same thing".

Announcement override is a special case: tapping an announcement plays it to the chosen zones at a set volume, ducks whatever was playing, and returns to the previous source when done. The mic has a push-to-talk version of the same: hold, speak, release, music comes back.

Presets save a full routing table ("Parade", "Festival day", "Everything off") and restore it in one tap.

08

Console

Served by the controller at https://civitone.local, or at whatever hostname the controller has. Built for a phone in one hand at the curb; the desktop view is the same screens with more room.

  • Overview. Status of every node at a glance, pending adoptions at the top, the latency profile, a master mute that cannot be missed.
  • Routing. Zone cards, source palette, presets, push-to-talk.
  • Node detail. Every heartbeat field, event log for that node, identify, reboot, forget, firmware update.
  • Sources. Level meters per input, announcement library, Bluetooth pairing.
  • Settings. Operator accounts, controller hostname, firmware images, backup of the registry.

A mockup of the console is published alongside this document as Civitone Console.

09

Build order

Each milestone is something that can be shown working on the bench, and each one keeps the previous ones working.

  1. Stock firmware baseline. Flash esparagus-snapclient on two Amped boards. Measure the lowest stable buffer. This sets the parade profile and validates the board before any custom code.
  2. Controller skeleton. Go service that wraps Snapcast, exposes the control WebSocket, serves a console that lists connected snapclients. No adoption yet.
  3. Control task in firmware. Heartbeat and commands over WebSocket. Console shows live status and can change volume.
  4. Adoption. Factory state, setup network, claim codes, tokens, forget. Node moves between the shop WiFi and a phone hotspot without being touched.
  5. Routing and presets. Source palette, linked groups, announcements, push-to-talk.
  6. Field pilot. One node on one pole at the next festival, controller on the operator's table.
  7. OTA updates and operator accounts. Needed before six nodes go up poles, not before.
